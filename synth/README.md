# Task synthesis

This directory holds the pipeline that authors LongWoF-Bench tasks. It is the
production side of the benchmark: it turns a one-line seed idea into a complete
`T = (S, E, Y, V)` task — public specification, environment, admissible
deliverable space, and a task-specific machine verifier — and then calibrates,
consolidates, and self-tests the resulting pool.

The evaluation side lives in [`../eval/`](../eval). Nothing here is needed to
*run* the benchmark; it is needed to *reproduce or extend* the task set.

## Layout

| Path | Contents |
|---|---|
| `shapes/<family>/seeds.txt` | Seed ideas, one `domain\|task_idea` per line |
| `shapes/<family>/prompts/` | The six authoring prompts, one per pipeline stage |
| `shapes/<family>/test_script.py.tmpl` | Family-shared oracle template |
| `*.py` | Pipeline drivers, described below |

`shapes/` covers the three synthesized families: `math_reasoning`,
`rule_following`, and `agent_env_synth`. The fourth family in the released
benchmark, `code_generation`, was carried over from an earlier curated track and
is not regenerated by this pipeline.

## The solution-first pipeline

`run_solution_first.py` is the current driver. Each candidate is produced by six
ordered model calls, each with its own gate, retry budget, and trace record:

| Stage | Output | Purpose |
|---|---|---|
| S1 design skeleton | `_design.json` | Fix the hard constraints before any prose exists |
| S2 reference solution | `reference_solution.py` | Compute the answer, and verify it is computable |
| S3 gold standard | `_gold.json`, `_fixture_manifest.json` | Freeze the answer and any fixtures |
| S4 task back-synthesis | `task.md` | Write the public spec *after* the answer, hiding the chain of steps |
| S5 oracle and foils | `test_script.py`, `_bad_solutions/` | Author the verifier and the near-misses it must reject |
| S6 skill | `SKILL.md` | Write the full-disclosure upper-bound manual |

Writing the specification last (S4, after S2 and S3) is what keeps the task
honest: the public prompt cannot quietly leak the derivation, because it is
authored against an answer that already exists.

`run_sample.py` is the earlier single-shot driver that predates this staging. It
is kept so the original approach stays reproducible; new work should use
`run_solution_first.py`.

## Stages after authoring

```
run_solution_first.py     author candidates          -> candidates_sf/
  retry_crashes.py          re-run crashed entries
  audit_env_host_pytest.py  retroactive host-pytest audit for agent_env
mini_calibration.py       difficulty calibration     -> keep / reject / isolate
consolidate.py            merge into the pool        -> tasks_final/
simplify_pool_layout.py   flatten to scenarios/, prune intermediates
promote_sanitized_skills.py  make the sanitized SKILL.md canonical
selftest.py               run every reference against its own oracle
```

`mini_calibration.py` is the difficulty gate. It renders each candidate with no
context, samples the anchor model `k` times, grades every trial through the
family's own oracle, and keeps only discriminating tasks:

- `n_pass == k` → **reject**, the task is trivially easy
- `n_pass == 0` → **isolate**, the task is broken or reasoning-hard
- otherwise → **keep**

`model_eval.py` is the synthesis-side evaluation harness used while building the
pool. Official results in the paper come from `eval/run_official.py`; use that
one for anything you intend to report.

## Running it

The pipeline calls a model provider and executes generated code. Read
[`../SECURITY.md`](../SECURITY.md) first — candidate execution is host
execution, and it belongs on a trusted, expendable machine.

```bash
# Credentials for the authoring model.
export GEMINI_API_KEY=...        # or write the key to ~/.gemini_key

# Author 10 rule-following candidates.
python synth/run_solution_first.py --family rule_following --n 10

# Calibrate difficulty, then consolidate what survived.
python synth/mini_calibration.py --family rule_following
python synth/consolidate.py --out-root tasks_final

# Verify every reference solution still satisfies its own oracle.
python synth/selftest.py --manifest tasks_final/manifest.json
```

`llm_client.py` also speaks to any OpenAI-compatible endpoint; set
`SYNTH_LLM=local` and `LOCAL_BASE_URL` to use one.

Candidates are written under `synth/candidates_sf/` (and `synth/candidates/`
for the single-shot driver). Those directories hold reference solutions and
gold answers, so they are ignored by Git and are rejected by
`tools/stage_c_release.py verify-code` — a checkout that has run the pipeline
is no longer the published tree, which is the intended behavior. Point
`--out-root` somewhere outside the repository if you would rather keep the
checkout pristine.

## What is not here

The pipeline writes private material that the public release deliberately
excludes: per-task verifiers, gold outputs, reference solutions, fixtures, and
authoring traces. Running the pipeline regenerates those locally. See
[the public release boundary](../README.md#public-release-boundary) for what the
published archive does and does not carry.
